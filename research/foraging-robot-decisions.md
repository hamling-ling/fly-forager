# 採餌ロボット — 機体側の決定シート

日付: 2026-11-20。`foraging-robot-design.md` §6 の決め事（状態／車体／糖センサー）に、
fly-car の実コード・実機構成を当てて判断材料を付けたもの。決定事項ではなく、
1行ずつ答えられる形のたたき台。設計ドラフト本体には触っていない。

前提（測り済み・検証済み）: 抽出回路 687 ニューロン／418,845 シナプスが全脳の
EC50 シフトを再現（base 72.1、H3 41.7、S3 105.0、閾値 60／40／100 で一致）。
1秒の試行が約1.0秒 — **ただし測ったのは共有 VM であって、UNO Q の MPU ではない**
（後述の「計算機はどこか」を参照）。

## 1. 状態 — 二値スイッチで始める（推奨）

- 測ったのは端点 H3／S3 だけ。連続状態は端点間の補間になるが、中間の値が
  正しい保証はなく、やるなら先に in silico で中間点（例: k_P 1.2、g_GABA 0.85）
  を測る必要がある。デモ台本（設計書 §4）は二値で成立する。
- 切り替えの駆動は「食べた回数」か「経過時間」で。どちらも展示用の操作で、
  実際のハエの空腹が二値だという主張ではない（設計書 §5 の留保どおり）。
- 答え方: 「二値で」／「連続にしたい（中間点の測定から）」

## 2. 車体 — 新規の小型車体（推奨）。fly-car 流用はしない

fly-car 側の実態（`src/flycar_q/README.md`、`sketch/motors.cpp` で確認）:

- UNO Q 1台、Sunplus 2K カメラ 1台、秋月 2WD プラットフォーム 1台、
  FT-SMC-2CH＋FM90×2（D3／D5 信号、単三4本の別電源）。共用できる予備はない。
- fly-car の実機走行は、非同期化マージ済み＋90°カメラの構成で**まだ未走行**。
  車体を借りると、そのリハーサルと競合し、コンテスト用の機体を崩すことになる。
- 採餌ロボットは「前に置かれたトークンを味わう」が主動作で、fly-car の
  ~100 ms ループや走行性能は要らない。流用の利点（部品代・組み立て済み）より、
  切り分けの利点が大きい。
- 答え方: 「新規の小型車体で」／「fly-car 流用で（リハーサルと順序を決めて）」

## 3. 糖センサー — まず色で始める（推奨）。導電率は後から

- 色: Sunplus カメラ＋既存の色閾値の流用が利く（90°カメラ用に refit 済みの
  `color_thresholds.json` の経路）。トークンを3段階の色の濃さにして
  公称 30／60／150 Hz に写す。弱点は照明依存 — デモ会場の照明で閾値の
  当たり直しが要る。
- 導電率: 照明に強いが、トークン側の作り込み（濡れ接点・糖水の保持）が要り、
  ハードもソフトも未検証。色で動くものを先に作り、乗り換えるなら後から。
- どちらでも、苦味チャンネルは別途要る。苦味耐性のデモは in silico 未実施
  （実験D §3.4）なので、初版のデモには入れない。
- 答え方: 「色で」／「導電率で」

## 4. 口吻サーボ — 位置決め用サーボが別途要る（FM90 は使えない）

- fly-car の FM90 は連続回転型で位置決めに向かない（設計書 §2.2 と同じ）。
  口吻には 9 g 級の位置決めサーボ（180°級、PWM 1000–2000 µs）が要る。
  `motors.cpp` の `Servo.writeMicroseconds`（1000–2000 µs）の経路が
  そのまま使える。車輪の D3／D5 とは別に、口吻用の PWM ピンが1本要る
  （fly-car では D3／D5 が車輪で塞がっている — 新規車体なら空きピンがある）。
- 電源は車輪と同じ規則で、UNO Q の 5 V からは取らない（別電源）。
- MN9→伸展角の換算は測り済みではない。案: 10 Hz で伸展開始、30 Hz で全伸展
  （設計書 §2.2 の案どおり）、デモで見て調整。
- 答え方: 機種選定は「位置決めサーボで」で進めてよいか

## 5. 計算機はどこか — まだ聞いていない1問（初版は PC／VM で、UNO Q は実測してから）

- 「1秒の試行が約1.0秒」は共有 VM での実測。UNO Q の MPU
  （Cortex-A53 ×4、RAM 2–4 GB）で Brian2 の部分回路が同じ pace で回るかは
  **未測定**。キノコ体の見積もり（`uno-q-mushroom-feasibility.md`）の MPU 側
  1–2 ms は小さな numpy プロトタイプの話で、Brian2 には当てはまらない。
- 推奨: 初版デモは PC／VM で回路を走らせ、車体とだけつなぐ。
  UNO Q 載せは、その後にボード上で1秒試行の実測を取ってから判断する。
  これなら「測ったものを載せる」が崩れない。
- 答え方: 「初版は PC／VM で」／「UNO Q 載せを先に測りたい」
